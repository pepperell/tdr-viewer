# M3 — Editor Shell: Detailed Plan

Goal: the WPF editing experience ([PLAN.md](../PLAN.md) §3.1–3.3, §6 M3). A Nodify canvas
where the user drags cables, loads, and connectors from a palette, wires them into arbitrary
networks (tees, stubs, rings), edits properties in an inspector, saves/loads projects, and
presses **Simulate** to render the engine's trace in the plot panel. Static trace on demand —
the debounced live pipeline, axis modes, and cursors are M4.

Starting point: the engine is complete and proven (M1+M2, 109 tests); the app is a stub —
an empty `NodifyEditor`, a `WpfPlot`, and a hardcoded demo network in
[MainWindow.xaml.cs](../src/TdrSim.App/Shell/MainWindow.xaml.cs). Nodify 7.3.0,
ScottPlot.WPF 5.1.59, and CommunityToolkit.Mvvm 8.4.2 are already referenced (M0).

**Architecture decision — the document model lives in `TdrSim.Core/Project/`, not the App.**
PLAN §4 placed "project save/load (JSON)" under Shell/; the *commands and dialogs* stay
there, but the serializable document and the document→`NetworkModel` compilation move to
Core, which has no UI dependencies. Rationale: this is where the real M3 bugs live (wire
graph → electrical nodes), and in Core it is unit-testable in the existing xUnit suite with
no WPF test host; the Nodify view models stay thin mirrors, which also preserves the
"Core + ViewModels port unchanged" portability goal (§2).

**Definition of done**

1. Core: `ProjectDocument` + `DocumentCompiler` with the test suite below green; all
   existing 109 tests still green; build clean (warnings as errors).
2. App launches showing the default branched demo document on the canvas (the M2 demo:
   30 m RG-58 → tee with 10 m open stub → 20 m RG-58 → open); **Simulate** renders the same
   trace the hardcoded M2 demo produced. The hardcoded `PlotDemoTrace` is deleted.
3. Palette drag-and-drop creates nodes at the drop point; ports accept multiple wires
   (3 wires at a port = tee); selection + Delete work; validation badges update as the
   graph changes.
4. Inspector edits (cable length/preset, load kind/values, connector preset, instrument
   settings) flow into the next Simulate.
5. Save → reopen round-trips canvas layout and all values; the reopened project compiles
   to an identical `NetworkModel` and simulates identically.
6. App launch smoke test passes (process starts, window titled, no crash on Simulate).

**Out of scope** (deliberate, to protect M4/M5): live/debounced recompute, γl-per-segment
memoization, axis mode switching, measurement cursors, reference traces, noise, undo/redo
(deferred to M5 polish; Delete is supported), fault elements, custom raw-RLGC cable entry.

## Step 1 — Project document (`Core/Project/ProjectDocument.cs`)

The serializable, UI-free description of what is on the canvas:

- `ProjectDocument { SchemaVersion = 1, Instrument, IReadOnlyList<DocumentNode> Nodes,
  IReadOnlyList<DocumentWire> Wires }`.
- `DocumentNode { string Id, DocumentNodeKind Kind, double X, double Y, … }` with a **flat
  nullable property bag** instead of JSON polymorphism (no `$type`, trivially versionable):
  `CablePresetId`, `LengthM`, `Z0OverrideOhms`, `VfOverride`, `LoadKind`, `ROhms`,
  `LHenries`, `CFarads`, `ConnectorPresetId`. Kinds: `Tdr`, `Cable`, `Connector`, `Load`,
  `Junction`.
- `DocumentWire { string FromNodeId, string FromPort, string ToNodeId, string ToPort }`.
  Port names are fixed per kind: two-ports expose `"A"`/`"B"`, one-ports (`Tdr`, `Load`,
  `Junction`) expose `"P"`.
- `InstrumentDocument { PresetId, RiseTimePsOverride, AmplitudeVoltsOverride,
  SourceImpedanceOverride }` → resolved against the catalog into `InstrumentSettings`.
- `ProjectSerializer`: System.Text.Json, camelCase, round-trips exactly; throws a clear
  message on missing/newer `schemaVersion`. File extension `.tdrproj`.

Tests (`ProjectDocumentTests`): serialize→deserialize structural round-trip including
positions and every property; unknown schema version throws; unknown node kind throws.

## Step 2 — Document compiler (`Core/Project/DocumentCompiler.cs`)

Turns a document into `(IReadOnlyList<DocumentIssue> Issues, NetworkModel? Model)`:

1. **Electrical nets by union-find** over terminals. Every (node, port) pair is a terminal;
   every wire unions its two terminals; `Junction` nodes union all wires landing on them
   and emit nothing. Each surviving class becomes one `NodeId`. This is the §7 mitigation:
   Nodify wires are port-to-port visuals, and any number of wires meeting at a port is one
   electrical node — a tee needs no special element.
2. **Element emission**: `Tdr` → `SourcePort`; `Cable` → `CableSegment` (preset spec from
   the catalog, `with`-cloned when Z0/VF overrides are set); `Connector` → `Connector`;
   `Load` → `Load`. A dangling two-port end is simply a one-terminal net — the engine
   already treats an unloaded node as an open, like a real unterminated cable (§3.2).
3. **Issues, not exceptions** (§3.2 "badges, not blockers"): `NoSource`,
   `MultipleSources`, `DisconnectedFromSource` (per island), `NonPositiveLength`,
   `InvalidLoadValues`, `UnknownPresetId`. Fatal issues ⇒ `Model = null`; the compiler
   never throws on user-reachable states. (Engine-level `ArgumentException`s become
   unreachable because the compiler pre-validates with the same rules.)

Tests (`DocumentCompilerTests`) — the heart of M3, written first:

- Chain document → `ChainExtractor.TryExtract` succeeds; `Simulate` gives the M1 answer
  (e.g. 30 m RG-58 + 75 Ω: `DcReflection` matches the divider to 1e−9).
- Tee document with three wires into one cable port → simulates with
  `Solver == SolverPath.Nodal` and DC = −1/3 ± 1e−9 (the case-9 network, now built from a
  document instead of hand-assembled elements).
- The same tee built through an explicit `Junction` node produces an identical Γ (junction
  is purely visual).
- Ring document (10 m + 20 m closing a loop) → compiles, simulates to the case-13 answers.
- Dangling cable end → same trace as the same network with an explicit `Open` load.
- No source / two sources / island / zero length / capacitor with no value → the right
  issue, `Model == null` only for fatal ones.
- Default document resource (step 7) compiles with zero issues.

## Step 3 — Shell layout (`App/Shell/`)

`MainWindow.xaml` becomes the §3.1 grid: toolbar (top), palette (left, 180 px), canvas
(center), inspector (right, 260 px), trace panel (bottom, existing `WpfPlot`).
`ShellViewModel` owns `EditorViewModel`, `PaletteViewModel`, `InspectorViewModel`,
`InstrumentViewModel`, the file commands (New/Open/Save/Save As), `SimulateCommand`, the
issue-badge collection, window title with dirty marker (`name*`), and a status line
(solver path, grid size, solve time, Settled warning). Code-behind keeps only what WPF
forces on it (file dialogs can live in a tiny service or the command handlers).

## Step 4 — Editor view models + Nodify templates (`App/Editor/`)

- `NodeViewModelBase` (Id, Location, IsSelected) with one subclass per kind; each exposes
  `PortViewModel`s (named `Port…`, never `Connector…` — that name is taken by the model
  element and by Nodify's own `Connector` control) and `ToDocumentNode()`.
- `ConnectionViewModel (PortViewModel Source, Target)`; `EditorViewModel` holds
  `Nodes`/`Connections` observable collections, implements Nodify's pending-connection
  pattern (`PendingConnectionViewModel` with start/complete commands), multi-wire ports
  (`PortViewModel` never refuses a connection), selected-items sync, and Delete (removes
  nodes plus their wires).
- `EditorViewModel.ToDocument()` is the **only** source for serialization and compilation;
  after any graph mutation it recompiles (cheap, O(graph)) to refresh the badge list and
  set the dirty flag. Follow the official Nodify sample (Playground/Calculator) patterns
  for `ItemContainer`/`NodifyEditor` template wiring.
- DataTemplates per node VM kind: TDR (port glyph + preset name), cable (name + length,
  A/B ports), connector, load (kind + value), junction (small dot, one port).

## Step 5 — Palette (`App/Editor/PaletteViewModel`)

Grouped `ItemsControl`: **Instrument** (TDR — disabled when one exists), **Cables** (one
item per catalog preset), **Connectors** (per preset), **Loads** (Open, Short, Resistor,
Capacitor, Inductor, Series RLC, Parallel RLC), **Junction**. WPF drag-drop: palette item
→ `DoDragDrop`; canvas drop handler converts the drop point through the editor's viewport
(location + zoom) into graph coordinates and asks `EditorViewModel` to create the node
with sensible defaults (RG-58 30 m, 50 Ω resistor, …).

## Step 6 — Inspector (`App/Editor/InspectorViewModel`)

`ContentControl` bound to the editor's single selection, `DataTemplate` per node VM:

- Cable: preset dropdown (catalog), length slider+box (0.1–1000 m, log scale) —
  slider+numeric pairs per §3.1; optional Z0/VF override boxes (blank = preset value).
- Load: kind dropdown + R/L/C boxes with unit suffixes (Ω, nH/µH, pF/nF), only the fields
  the kind uses.
- Connector: preset dropdown.
- TDR node or empty selection: instrument panel (preset dropdown + rise time, amplitude,
  Z_ref overrides) — the same `InstrumentViewModel` the toolbar preset selector binds to.

Every edit marks the document dirty and re-runs compile-for-badges; nothing simulates
until the user asks (M3 contract).

## Step 7 — Save/load + default document (`App/Shell/`)

- New/Open/Save/Save As over `ProjectSerializer` (`.tdrproj`, JSON), standard dialogs,
  unsaved-changes prompt on New/Open/close. Document → VM hydration lives next to
  `ToDocument()` so the mapping is one pair of functions.
- The M2 demo network ships as an embedded resource `default.tdrproj` (with hand-placed
  canvas coordinates) and loads at startup — replacing `PlotDemoTrace()` entirely. Its
  content doubles as the step-2 "default document compiles clean" test fixture.

## Step 8 — Simulate on demand (`App/Shell/`)

`SimulateCommand`: compile → if fatal issues, focus the badge list; else `Task.Run`
`TdrSimulator.Simulate` (default `SimulationSettings`), one run in flight (button disabled
while running), then update the plot on the UI thread: Ω vs distance exactly like the M1/M2
demo (axis modes arrive in M4), title from the file name, `Settled == false` → warning
badge "trace not settled — increase time span" (§1.4.7). Simulation exceptions land in a
status message, never a crash.

## Step 9 — Validation badges (`App/Shell/`)

Toolbar chip per distinct issue kind with count and tooltip (e.g. "2 cables have zero
length"), driven by the compile-on-mutation results from step 4. Badges are advisory;
only fatal ones block Simulate (by producing no model).

## Step 10 — Smoke pass

Full test suite; app launch smoke (start, title check, Simulate via default document still
computes — verified by the absence of the error status on startup auto-simulate? No:
M3 keeps simulate manual; the smoke test just launches and checks the window). Manual
checklist: drag each palette kind, wire a tee, edit length, save, reopen, simulate, delete
a node, badge appears on dangling source removal.

## Sequencing

1 → 2 in Core, test-first (the compiler tests pin every graph semantic before any XAML
exists). Then 3 (layout) → 4 (editor VMs — the long pole) → 5 (palette) → 6 (inspector) →
7 (save/load + default doc) → 8 (simulate) → 9 (badges) → 10 (smoke). Steps 5/6 are
independent after 4; 8 and 9 are independent after 7.

## Risks

| Risk | Mitigation |
|---|---|
| Nodify specifics (pending connections, viewport-relative drop coordinates, selection sync) | Follow the official Nodify Playground/Calculator sample patterns; version pinned at 7.3.0; the §7 fallback (vendor/fork, MIT) stands |
| Name collisions: `Model.Connector` element vs Nodify's `Connector` control | Convention fixed in step 4: view models say `Port…`; XAML uses the `nodify:` prefix explicitly |
| VM ↔ document drift (edits that serialize but don't compile, or vice versa) | `ToDocument()` is the single path into both the serializer and the compiler; hydration is its one inverse; compiler tests pin the semantics |
| JSON polymorphism fragility | Flat nullable property bag + explicit `schemaVersion`; unknown kinds/versions fail loudly (tested) |
| WPF code is hard to unit test | Everything that can be wrong in interesting ways (net resolution, validation, serialization) lives in Core and is tested there; VMs are thin mirrors; app gets a launch smoke test + manual checklist |
| Scope creep toward M4 (it's tempting to make the trace live) | Hard line: no debounce, no memoization, no cursors, no axis modes in M3 — Simulate is a button |
| Editing UTF-8/em-dash files with PS 5.1 round-trips (mojibake, hit twice before) | All file edits via the Write/Edit tools only |
